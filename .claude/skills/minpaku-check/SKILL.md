# 民泊チェック 実行手順

「民泊チェック」と依頼されたら、必ずこの手順で行う。**一部のソースだけ見て結論を出さない。**

## 鉄則

1. **推測で埋めない。** 読めないデータがあれば、そのソースは「未取得」と明記する。
   未取得のまま出した数字・結論には必ずその旨を付ける。
2. **止まるか、見えた分で出すかはユーザーが決める。** 原則は「見えるデータで即レポート」し、
   レポート末尾に必ず「🔍 このデータがあればさらに分かること」を付けて、何を渡せば
   どこまで深掘りできるかを具体的に書く（下記テンプレ参照）。
3. **PriceLabsの稼働率を鵜呑みにしない。** PriceLabsはカレンダーブロックを「稼働」として
   数える。マンスリー貸し・手動ブロックがある物件（特に新子安）では実予約と乖離する。
   必ずBeds24予約またはシミュレーターの予約データと突き合わせる。
4. **マンスリー（28泊以上）を必ず見る。** シミュレーターは28泊以上を「長期」として
   ADR・稼働率から除外して売上のみ計上する設計（`isLongStayListing`）。
   契約書PDFはGoogle Drive（「新子安民泊」フォルダ等、`一時使用` `Lease` で検索）にある。
   契約期間とAirbnb予約の日付ズレ（例: 契約8/31〜10/1 vs 予約9/1〜9/30）は境界泊として注記する。

## データソースと取得経路

| # | ソース | 取得経路 | 取れるもの |
|---|--------|---------|-----------|
| 1 | 民泊シミュレーター | Google Drive「民泊バックアップ」内の最新 `minpaku_check_*/simulator_backup.json`（旧: `minpaku_backup_*.json`） | 全予約（Airbnb/Booking.com/マンスリー）・物件設定・実費・履歴 |
| 2 | Beds24 | 同フォルダの `beds24_bookings.json` / `beds24_calendar.json` | 全チャネル予約・**日別の価格/min stay/在庫** |
| 3 | Airbnb | 同フォルダの `airbnb_insights_raw.txt`（または `_manual.json`） | **閲覧数・成約率** |
| 4 | Booking.com | 同フォルダの `bcom_extranet_raw.txt`（または `_manual.json`） | **閲覧数・掲載パフォーマンス** |
| 5 | PriceLabs | MCPで直接取得（このセッションから叩ける） | 推奨価格・市場需要・市場稼働・pace |

- 1〜4はユーザーのMacで `python3 collect_minpaku_data.py` を実行すると1フォルダにまとまり、
  Driveの「民泊バックアップ」に置かれる。**3日以上古い場合はその旨を明記**し、
  再実行を依頼する（依頼した上で、見える分のレポートは出す）。
- Beds24 API・Firebase RTDB はこの実行環境から**直接は叩けない**（ネットワークポリシーで403）。
  直接試して時間を浪費しない。

### PriceLabsで必ず叩くもの

- `get_listings` → `get_pms_reservations`（pms=beds24 と pms=airbnb の両方・滞在日で広めに）
- `get_listing_prices`（今日〜90日先: 配信価格 vs `uncustomized_price`=推奨 vs 下限貼り付き）
- `get_listing_health_and_recommendations`（min stay等の推奨）
- `get_listing_performance_metrics`（市場比較。**稼働率は鉄則3の注意つきで**）

## 分析の必須項目

1. **データ鮮度表**: 各ソースの取得日時と状態（✅/🟡/❌）を表で先頭に。
2. **予約サマリ**: チャネル別（Airbnb直/Booking.com/マンスリー）に件数・泊数・売上（gross/net）。
   ソース間で件数・金額を突き合わせ、不一致は明示。
3. **日別グリッド（今日〜60〜90日）**: 日付 × { 予約済/ブロック/空室、自社価格、PriceLabs推奨、
   min stay、市場需要 }。フラグ: 下限価格貼り付き・min stayが市場推奨超え・
   高需要日なのに空室・ブロックの理由不明。
4. **ペースと閲覧数**: 直近7/30日の新規予約とリードタイム、Airbnb/Booking.comの閲覧数と
   成約率の推移。閲覧多×成約無=価格/条件の問題、閲覧少=露出の問題、と切り分ける。
5. **マンスリー損益比較**: マンスリーの実質泊単価（手数料後） vs 同期間デイリーの実RevPAR。
   次のマンスリー契約のパイプライン（契約書がDriveにあるか）。
6. **アクション提案**: 優先度順・概算金額インパクト付き。

## レポート形式

```
① データ鮮度表（✅🟡❌）
② 予約サマリ（チャネル別・ソース突き合わせ）
③ 日別グリッドと警告フラグ
④ ペース・閲覧数
⑤ マンスリー損益
⑥ アクション（優先度順・金額付き）
⑦ 🔍 このデータがあればさらに分かること（未取得ソースごとに、
   「何を渡せば」→「何が分かるようになるか」を1行ずつ具体的に）
```

⑦の例:
- 「`collect_minpaku_data.py` を実行してDriveに置く」→ 日別の自社価格・在庫が入り、
  下限貼り付きと機会損失を日単位・金額で出せる
- 「Airbnbインサイト画面を開いた状態で実行 or 閲覧数を手入力」→ 閲覧→予約の
  ファネルが引けて、価格が高いのか露出が無いのかを切り分けられる
